GitHub 8月17日宕机源于VS Code重试缺陷与AI流量激增

新闻时间: 2026-08-21T02:36:17.709902+00:00 · 来源: hackernews

8月17日，GitHub遭遇持续近八小时的全球性服务中断，影响范围涵盖API、Actions、Webhooks及Copilot Token服务。事件最初仅是美国某数据中心的容量瓶颈，却迅速演变为平台级故障——并非单纯因服务器过载，而是由多重依赖失效引发的连锁反应。当Copilot Token服务响应延迟时，一个长期潜伏在Visual Studio Code中的重试机制被意外触发：客户端未优雅降级，反而以高频率、无退避策略反复请求，导致流量激增约10倍。这场“重试风暴”压垮了本已承压的后端系统，使局部延迟升级为全站瘫痪。

事后分析揭示出两大深层问题：其一，客户端重试逻辑（尤其在VS Code等广泛使用的IDE中）缺乏指数退避、随机抖动或熔断机制；其二，底层压力来自爆炸性增长——自4月以来，月度代码提交量从14亿跃升至29亿，四个月内翻倍。其中大量新增负载源自AI工具链，尤其是Copilot在编码过程中高频、低延迟的令牌请求。

GitHub的复盘报告坦率承认：其基础设施扩展能力（包括自动扩缩容配置失误、对客户端行为可观测性不足）未能跟上AI重塑的使用模式。公司已紧急上线多项改进：对Token端点实施速率限制、增加客户端重试行为遥测、并与微软协同修复VS Code的重试逻辑。但工程师和平台观察者指出更根本的矛盾：AI驱动的增长并未同步带来相匹配的收入增长，免费服务在极端负载下的可持续性正面临严峻考验。

此次事件已成为现代平台工程的经典案例。它警示业界：客户端行为本身，而非仅服务器容量，已成主导性故障源。当开发者工具深度集成AI助手，韧性设计必须重构——重试策略不再是后端单方面责任，而是客户端、IDE与云服务之间必须共同遵守的分布式系统契约。对所有基于GitHub（或任何AI高负载平台）构建应用的团队而言，这一课清晰而紧迫：优雅降级与审慎的重试策略，已是基础设施的刚性要求。
