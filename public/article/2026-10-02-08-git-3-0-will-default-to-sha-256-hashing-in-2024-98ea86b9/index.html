Git 3.0 将默认启用 SHA-256 哈希算法

新闻时间: 2026-10-02T06:58:44.044078+00:00 · 来源: hackernews

Git 正在为一项基础性的密码学升级做准备：从 3.0 版本起，新建仓库将默认采用 SHA-256 替代 SHA-1 作为对象标识哈希算法。这一变化远不止是表面调整——它将重塑 Git 存储、校验和跨生态交换数据的方式。该迁移已开发多年，SHA-256 支持早在 Git v2.42（2023 年 7 月）中就已稳定，并被正式标记为“非实验性”。尽管向后兼容仍是重点——现有 SHA-1 对象可与 SHA-256 对象共存，且仍能被正常引用——但切换过程确实带来了真实工程挑战，尤其体现在子模块、代码托管平台及工具链互通性方面。

一场激烈讨论因一篇题为《Git 3.0 即将默认启用 SHA-256 是个代价高昂的错误》的博客文章而升温。该文认为此次迁移技术上不必要、经济上浪费，且在大规模场景下难以落地，声称 SHA-1 在 Git 场景中依然实际安全，SHAttered 等碰撞攻击不会危及仓库完整性。但 Hacker News 上多位专家迅速指出其技术误判：SHAttered 并非纯理论——它于 2017 年就实现了对 SHA-1 的高效、实用碰撞攻击；Git 之所以未受直接影响，仅因攻击者尚未针对 Git 对象前缀格式做专门优化。

评论还纠正了原文多处事实错误，例如误判 GitHub 当前能力（GitHub 确实尚未支持 SHA-256 仓库，但这属于托管平台实现滞后，而非 Git 协议本身限制），也低估了其他工具的响应速度。例如，Fossil SCM 在 SHAttered 公布仅六天后就完成了 SHA3-256 支持。与此同时，Git 官方迁移文档明确回应了互操作性关切：SHA-1 与 SHA-256 对象之间存在双向映射关系，分支名、文档中的提交哈希等引用方式完全不受哈希格式变更影响。

归根结底，SHA-256 迁移反映的是整个行业淘汰过时密码学原语的大趋势——这不仅关乎理论上的未来防护，更因维持 SHA-1 已日益违背安全策略、合规要求及现代工具链预期。虽然落地需多方协同，但它避免了更昂贵的局面：即在漏洞真正爆发后仓促补救。
