Ruff v0.16.0 enables 413 linting rules by default, breaking many CI pipelines

News time: 2026-07-26T04:37:41.926704+00:00 · Source: rss

Ruff v0.16.0, released on July 23, 2026, marks a pivotal shift in Python static analysis — not through speed or syntax, but through scope. The widely adopted Rust-based linter now enables 413 rules by default, up from just 59 in prior versions. This isn’t incremental tuning: it’s a deliberate expansion of what Ruff considers critical enough to flag without configuration. As developer Simon Willison discovered, the update broke CI jobs across his major open-source projects — Datasette, sqlite-utils, and LLM — all because their dependencies pulled the unpinned latest Ruff version automatically.

The change reflects Ruff’s maturation: since its v0.1.0 release, the total rule count has grown from 708 to 968, with many new rules targeting high-impact issues previously left unenforced — like calling datetime.datetime.now() without a timezone (DTZ005), catching bare Exception (BLE001), or performing useless attribute access (B018). These aren’t stylistic nits; they’re patterns that can cause runtime failures, subtle bugs, or security weaknesses. Crucially, Ruff now surfaces them out of the box, eliminating the need for teams to manually curate rule sets.

Willison’s hands-on testing revealed the scale: running ruff check . --fix --unsafe-fixes on sqlite-utils fixed 1,538 of 1,618 reported errors in one go — a testament to both Ruff’s precision and its growing automation capability. Notably, the tool’s output is structured and explanatory, making it ideal not only for human developers but also for AI coding agents: GPT-5.6 Sol and Claude Opus 5 were successfully used to auto-generate PRs fixing hundreds of violations across repositories.

This update underscores a broader trend: static analysis tools are evolving from optional style enforcers into foundational safety layers. With Ruff now catching real runtime hazards by default — and doing so at speeds 10–100× faster than Flake8 — it’s becoming less a 'nice-to-have' linter and more an essential gatekeeper in Python development workflows. For maintainers, the immediate takeaway is clear: pin your Ruff version in CI, audit the new defaults, and treat linting as part of your correctness contract — not just code hygiene.
