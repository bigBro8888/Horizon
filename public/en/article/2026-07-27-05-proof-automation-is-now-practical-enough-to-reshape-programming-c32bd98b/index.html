Proof automation is now practical enough to reshape programming

News time: 2026-07-27T04:49:50.416687+00:00 · Source: hackernews

A new post by Adam Langley—author of widely used cryptography libraries and longtime security engineer at Google—argues that proof automation has crossed a threshold: it’s no longer a theoretical ideal but a deployable tool. He observes that modern theorem provers like Lean 4 and Verus, combined with advances in large language models (LLMs), are beginning to automate verification tasks that once required months of expert labor. Rather than writing hundreds of unit tests, developers may soon write precise formal specifications—and let tools automatically prove correctness against them.

Langley doesn’t claim we’re done with testing. Instead, he describes a cost-benefit inflection point: where formal verification used to cost 20× more than development, automation and LLM-assisted proof scripting are collapsing that gap. Projects like the Ethereum Virtual Machine formalization in Lean 4—completed in about a week using LLM inference—show how quickly high-assurance artifacts can now be generated. Similarly, Verus, a Rust-based language embedding separation logic and automated proofs, demonstrates how verification can be woven into the type system itself.

The shift isn’t just technical—it’s economic and cultural. As one commenter notes, Mythos—a formal-methods-driven security team—has found more vulnerabilities in real-world systems than the broader security industry combined, underscoring how much latent risk remains in unverified code. Meanwhile, tools like SpecVerify and VeriPlan show how LLMs can bridge natural-language requirements to machine-checkable specs, lowering the barrier for non-specialists. The bottleneck is no longer proof generation—it’s specification clarity.

This doesn’t mean every developer must become a logician overnight. But it does suggest a new division of labor: programmers increasingly act as specification engineers, defining what must hold, while automation handles how to prove it. Langley concludes that the next decade will see programming languages evolve to treat proofs not as optional add-ons—but as first-class, compiler-checked artifacts—just like types or memory safety today.
