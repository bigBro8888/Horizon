uv 0.12.0 defaults to uv_build in new projects

News time: 2026-07-29T04:27:46.872737+00:00 · Source: github

The Python tooling ecosystem just got a meaningful nudge toward modern project standards: uv 0.12.0, released on July 28, 2026, now initializes new projects with a full build system by default — using uv_build, its own high-performance, PEP 517–compliant backend. This change marks a deliberate return to best practices after years of offering minimal, unpackaged layouts for simplicity. The new default places source code under src/, declares a [build-system] table in pyproject.toml, and adds a CLI script entry — making projects immediately installable, importable, and runnable via uv run. It’s not just convenience: it aligns new projects with how real-world Python packages are structured and consumed.

This shift follows the stabilization of uv_build earlier this year — benchmarks show it’s 10–35× faster than alternatives like hatchling or setuptools. The team explicitly designed uv_build for tight integration with uv’s resolver and installer, reducing overhead and eliminating redundant dependency resolution during builds. While the change is labeled "breaking" out of caution, existing projects remain untouched, and users who prefer the old bare-bones layout can opt out with uv init --no-package.

Beyond project initialization, uv 0.12.0 tightens security and spec compliance. It now rejects source distributions archived with .tar.bz2 or .tar.xz (per PEP 625), allowing only .tar.gz — and disallows wheel entries compressed with bzip2, LZMA, or XZ, permitting only stored, DEFLATE, or zstd. These restrictions shrink uv’s compression dependencies and reduce attack surface when installing untrusted packages. Additionally, uv now blocks all case variants of python (e.g., Python, PYTHON) as wheel entry points — preventing accidental overwrites of the interpreter binary on case-insensitive filesystems like those used by macOS and Windows.

The release reflects mature stewardship: breaking changes come with clear migration paths, backward compatibility guarantees for most workflows, and thorough documentation. Configuration for existing uv_build-based projects requires only updating version bounds in pyproject.toml (e.g., uv_build>=0.11.32,<0.13). No major behavioral regressions are reported, and the team emphasizes that the vast majority of users should upgrade seamlessly.
