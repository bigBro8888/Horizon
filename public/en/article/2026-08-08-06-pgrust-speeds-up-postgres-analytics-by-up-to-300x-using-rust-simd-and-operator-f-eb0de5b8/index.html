pgrust speeds up Postgres analytics by up to 300x using Rust, SIMD, and operator fusion

News time: 2026-08-08T02:59:47.556064+00:00 · Source: hackernews

A new experimental PostgreSQL extension called pgrust has demonstrated dramatic speedups—up to 300 times faster—for analytical workloads. Developed by engineer malisper, pgrust is not a patch or optimizer layered on top of PostgreSQL, but a ground-up rewrite of the query execution engine in Rust. It retains full compatibility with PostgreSQL’s wire protocol, SQL semantics, and on-disk format, meaning existing applications can connect without modification—though it currently runs as an extension, not a standalone replacement.

The performance leap comes from three core technical innovations: batching (processing data in chunks rather than row-by-row), operator fusion (merging sequential operations like filter-project-join into single optimized passes), and SIMD acceleration (leveraging modern CPU vector instructions to process multiple values in parallel). These techniques are common in high-performance analytical databases—but rarely applied so deeply within a production-grade, transaction-safe system like PostgreSQL.

Crucially, pgrust doesn’t sacrifice correctness for speed. The author emphasizes formal verification—proving over 1,000 user-facing functions behave identically to upstream PostgreSQL—and differential fuzzing, where identical SQL queries are executed against both pgrust and vanilla PostgreSQL to catch semantic mismatches. This dual validation approach is unusually rigorous for an early-stage database project and directly addresses the biggest barrier to adoption: trust.

Still, pgrust remains experimental. Its GitHub README warns it is not production-ready, lacks support for existing PostgreSQL extensions, and has no stable ABI. It currently passes PostgreSQL’s full regression test suite—a strong signal—but real-world workloads may expose edge cases. Community reactions reflect this tension: some praise its technical ambition and potential to push PostgreSQL’s architecture forward; others question whether speed gains justify replacing a battle-tested, community-maintained codebase—especially when alternatives like kdb+ already deliver extreme throughput for niche analytical use cases.
