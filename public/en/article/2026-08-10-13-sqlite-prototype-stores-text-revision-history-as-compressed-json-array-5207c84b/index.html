SQLite prototype stores text revision history as compressed JSON array

News time: 2026-08-10T03:17:51.569128+00:00 · Source: rss

A new experimental approach to versioning text in SQLite databases proposes storing full revision histories—not as separate rows or diffs—but as a single, zlib- or zstd-compressed JSON array of all prior versions. Developer Simon Willison conceived the idea during a dog walk, reasoning that repeated content across successive edits (e.g., paragraphs unchanged between revisions) creates high redundancy ideal for compression. Instead of appending a new 20 KB row for every edit of a long document, the prototype bundles all versions into one binary BLOB column—dramatically reducing storage overhead.

The core insight is simplicity: a table holds two columns—one BLOB containing zstd-compressed JSON like ["v1 text", "v2 text", "v3 text"], and another TEXT column storing uncompressed timestamps as a JSON array of Unix seconds. Early tests simulated 1,000 edits to a document and found raw revision data totaling 20.4 MB shrank to just 80.3 KB after zstd compression—a 254× reduction. That efficiency stems not from clever delta encoding, but from leveraging general-purpose compression algorithms on highly repetitive string sequences.

However, updating such a monolithic blob on every edit would require full decompression, modification, and recompression—costly for large histories. To address this, the prototype adopts a pragmatic partitioning strategy: splitting the history across multiple rows, each capped at either 128 revisions or 3 MB of uncompressed JSON. This balances compression gains with update performance, making the scheme viable for real-world embedded or edge applications where disk space and CPU are constrained.

While still a prototype without benchmarks on query latency, transaction safety, or concurrency, the design reflects a broader shift toward rethinking database versioning beyond traditional models like temporal tables or audit logs. It’s especially relevant for local-first apps, note-taking tools, or collaborative editors built atop SQLite—where lightweight, self-contained, and portable history storage matters more than enterprise-grade ACID guarantees. As Willison notes, it’s less about replacing Git and more about solving the ‘tiny versioning’ problem where every kilobyte counts.
