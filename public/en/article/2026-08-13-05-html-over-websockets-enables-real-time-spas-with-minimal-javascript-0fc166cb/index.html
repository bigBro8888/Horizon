HTML over WebSockets enables real-time SPAs with minimal JavaScript

News time: 2026-08-13T03:32:13.942554+00:00 · Source: hackernews

A growing number of developers are rethinking how modern web applications handle interactivity — not by shipping more JavaScript to the browser, but by sending fully rendered HTML fragments directly over WebSockets. This approach, dubbed 'HTML over WebSockets', sidesteps traditional client-side frameworks like React or Vue. Instead, the server renders HTML on demand and pushes it instantly to connected clients, enabling real-time updates without custom frontend logic.

The idea isn’t entirely new: Chris McCord pioneered it first in Rails Sync around 2013 — a proof-of-concept for real-time partial updates in Ruby on Rails — before refining and scaling it into Phoenix LiveView in 2019. LiveView demonstrated how Elixir’s lightweight processes could serve dynamic, interactive UIs over persistent WebSocket connections, all while keeping rendering and state logic firmly on the server.

Today, the pattern is gaining traction beyond Elixir. Django developers use libraries like Sockpuppet and Reactor; Rubyists rely on Turbo and Hotwire (which uses SSE or HTTP, not WebSockets, but shares the same philosophy); and even plain HTML + minimal JS can integrate with WebSocket backends using standard APIs. The core trade-off is clear: reduced frontend complexity and faster iteration at the cost of higher server memory usage and connection management overhead.

Critics rightly point out that WebSockets aren’t always necessary — Server-Sent Events (SSE) suffice for one-way server pushes, and htmx over HTTP works well for simpler interactions. But for true bidirectional, low-latency collaboration — think live dashboards, shared editing, or real-time forms — WebSockets remain unmatched. As one commenter noted, the right tool depends less on fashion and more on the problem: latency requirements, data flow direction, and team expertise.

Ultimately, HTML over WebSockets represents a philosophical shift — away from ‘client-first’ architecture toward ‘server-rendered, real-time by default’. It doesn’t replace JavaScript, but redefines its role: no longer orchestrating state and DOM updates, but merely establishing and managing the connection.
