Practitioner seeks robust one-class anomaly detection for performance regression with only 10 healthy hardware counter samples

News time: 2026-08-14T03:28:57.937634+00:00 · Source: reddit

A systems engineer working on automated performance regression detection has posted an urgent, technically precise question to the Machine Learning subreddit: how to rigorously apply one-class anomaly detection when training data is extremely scarce—just ten healthy runs measured via CPU hardware performance counters. Unlike typical supervised ML tasks, this setup assumes no labeled anomalies during training; instead, the model must learn a tight representation of ‘normal’ behavior from sparse, high-dimensional counter data—such as L1 cache misses, branch mispredictions, or instruction-retirement rates—and later flag deviations in new builds or configurations as potential regressions.

The core challenge lies in statistical validity under severe data constraints. With only ten healthy samples, standard train/validation/test splits become meaningless: a 60/20/20 split would leave just two or three samples for validation—too few to reliably estimate threshold sensitivity or false positive rate. The author currently uses leave-one-out (LOO) cross-validation on the healthy set to calibrate detection thresholds, but questions whether that’s sufficient—or even appropriate—for one-class methods like One-Class SVM or autoencoder-based approaches. They’re also uncertain whether unseen regression runs can serve directly as test data, or if a second independent healthy dataset is needed to assess real-world false positive risk.

Evaluation strategy adds another layer of complexity. Since the goal is binary detection—not predicting counter values—the author rightly rejects regression metrics like MSE or MAE. Instead, they focus on detection rate (recall) and false positive rate, which align with operational needs: catching real regressions without flooding CI/CD pipelines with false alarms. Yet selecting the right threshold remains fraught: too strict, and subtle but meaningful regressions go unnoticed; too lenient, and noise triggers unnecessary investigations.

This isn’t just theoretical. Hardware counters are low-overhead, OS-agnostic signals deeply tied to microarchitectural behavior—making them ideal for early, precise regression spotting in compilers, kernels, or database engines. But their sparsity and event multiplexing (where counters are shared and rotated across measurements) mean each sample is noisy and incomplete. Rigorous methodology here bridges ML practice and systems engineering: it determines whether ML-powered observability can be trusted in production-grade performance CI.
