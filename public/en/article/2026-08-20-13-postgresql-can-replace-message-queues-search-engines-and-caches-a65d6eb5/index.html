PostgreSQL can replace message queues, search engines, and caches

News time: 2026-08-20T02:21:36.684600+00:00 · Source: hackernews

A growing number of engineers are rethinking infrastructure complexity—not by adding more tools, but by leaning harder on PostgreSQL. In a widely discussed essay titled PostgreSQL for Everything, developer Raphael Bauer argues that modern PostgreSQL isn’t just a relational database anymore. With features like logical replication (introduced in v10), efficient JSONB storage, built-in full-text search, and the lightweight pub/sub mechanism LISTEN/NOTIFY, it can absorb responsibilities once reserved for Kafka, Elasticsearch, Redis, or even time-series or vector databases—at appropriate scale.

The case isn’t theoretical. Revolut, a digital bank processing millions of financial events daily, uses PostgreSQL as its sole event persistence and streaming layer—no Kafka or RabbitMQ. They rely on logical replication to fan out events and LISTEN/NOTIFY for real-time application coordination. Similarly, developers report using pgvector for semantic search and TimescaleDB (a PostgreSQL extension) for time-series workloads—all within the same database instance. This ‘Postgres-first’ approach reduces operational overhead, simplifies data consistency, and avoids cross-service serialization and network latency.

Yet the article doesn’t claim universal supremacy. It explicitly acknowledges trade-offs: PostgreSQL’s full-text search lacks Elastic’s relevance tuning and distributed scaling; its LISTEN/NOTIFY isn’t durable or ordered like a true message broker; and high-throughput vector or time-series workloads may strain shared resources when co-located with transactional traffic. The pragmatic advice echoed across the community is clear: start with PostgreSQL, measure where it breaks, and only then introduce specialized tools.

This philosophy reflects a broader shift in systems design—from polyglot persistence (many best-of-breed tools) toward pragmatic consolidation. It’s not about eliminating specialization, but delaying it until necessity—and measurable cost—demands it. For startups, mid-sized teams, or applications with moderate scale and evolving requirements, PostgreSQL increasingly serves as a capable, unified foundation—not because it does everything perfectly, but because it does enough, well, and reliably.
