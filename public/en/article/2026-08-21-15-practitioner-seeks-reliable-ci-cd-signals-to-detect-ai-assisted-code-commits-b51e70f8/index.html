Practitioner seeks reliable CI/CD signals to detect AI-assisted code commits

News time: 2026-08-21T02:36:17.214983+00:00 · Source: reddit

A software engineer is building a system to estimate the likelihood that code committed to a Git repository was generated or significantly assisted by AI coding tools. Rather than relying on source-code style analysis—like perplexity or burstiness metrics—they’re focusing on process-level signals available at commit and CI pipeline time: commit trailers (e.g., AI-Generated: true), lines of code added or deleted, number of files changed, edit density, and commit frequency patterns. But early results show these signals are noisy: a 500-line addition could reflect scaffolding from GitHub Copilot—or a seasoned developer refactoring legacy logic. Worse, metadata like AI trailers can be manually edited or omitted, and provenance erodes once code leaves the IDE and enters version control.

The core challenge isn’t detection accuracy alone—it’s calibration. The engineer explicitly rejects binary classification (‘AI’ vs ‘human’) in favor of probabilistic risk scoring: “even a reliable way of estimating ‘this commit has a high probability of AI assistance’ with measurable false-positive/false-negative rates would be useful.” This framing reflects growing industry realism: perfect attribution is unattainable, but actionable risk signals—especially for compliance, license review, or security triage—are urgently needed.

They’re also asking upstream questions: Can provenance be preserved earlier? Should AI tooling emit cryptographically signed, verifiable metadata into CI pipelines? Projects like Tabnine’s provenance integration and SLSA-compliant build attestations point toward embedding trust by design, not retrofitting it post-commit. Meanwhile, Git trailers remain a lightweight, widely supported convention—but only if adopted consistently and protected against tampering.

Ultimately, this isn’t about policing developers. It’s about enabling responsible AI adoption: knowing where AI touches code helps teams enforce licensing policies, assess technical debt, audit security implications, and meet emerging regulatory expectations (e.g., EU AI Act supply chain transparency requirements). As one commenter noted, the goal isn’t surveillance—it’s traceability with intent.
