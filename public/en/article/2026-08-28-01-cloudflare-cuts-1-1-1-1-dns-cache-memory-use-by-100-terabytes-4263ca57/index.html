Cloudflare cuts 1.1.1.1 DNS cache memory use by 100 terabytes

News time: 2026-08-28T12:44:25.523449+00:00 · Source: hackernews

Cloudflare has dramatically reduced the memory footprint of its globally used 1.1.1.1 DNS resolver—by a staggering 100 terabytes—through a series of low-level, systems-oriented optimizations in Rust. This isn’t theoretical tuning: it’s production-grade engineering applied at planetary scale. The 1.1.1.1 service handles over 25 million DNS queries per second across more than 300 data centers, caching billions of DNS records to deliver fast, privacy-respecting resolution. Every byte saved multiplies across thousands of servers—and this optimization freed enough RAM to replace the entire memory capacity of over 130 of Cloudflare’s latest-generation servers.

The improvements came from five tightly coordinated changes to how DNS cache entries are laid out and managed in memory. First, Cloudflare redesigned the CacheEntry struct to minimize padding and align fields for 64-bit efficiency—applying lessons long known in C but rarely prioritized in high-level services. Second, they replaced separate heap allocations for record payloads with embedded inline storage, eliminating pointer indirection and allocation overhead. Third, they introduced a custom slab allocator tuned specifically for fixed-size DNS entries, reducing fragmentation and metadata bloat. Fourth, they unified multiple independent lists (e.g., for TTL tracking and eviction) into a single compact arena, trading some Rust type-safety guarantees for massive memory density gains. Fifth, they optimized string handling by interning domain names and reusing buffers across query-response lifecycles.

These changes cut per-entry memory usage by 56%—from an average of ~1.2 KB to ~0.53 KB—without sacrificing correctness, safety, or performance. In fact, the cache became measurably faster: lower memory pressure improved CPU cache locality, and fewer allocations reduced lock contention. The work was done incrementally, validated with real-world traffic traces and A/B testing across server fleets—no speculative rewriting, just disciplined measurement-driven iteration.

What makes this especially notable is that it happened after 1.1.1.1 had already achieved massive scale and stability. As one engineer noted on Hacker News, optimization wasn’t the first step—it was the last, applied only once the system was proven, profitable, and deeply understood. That discipline—building first, optimizing later, and doing so with surgical precision—is what turned a routine infrastructure task into a landmark case study in modern systems programming.
