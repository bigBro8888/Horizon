Anubis ships WebAssembly after one year of compatibility work

News time: 2026-09-07T06:04:01.432360+00:00 · Source: hackernews

After a full year of engineering effort, the Anubis project — a privacy-focused, client-side challenge system often used as a CAPTCHA alternative — has officially shipped WebAssembly support. Unlike typical WASM rollouts that target modern browsers, this integration prioritizes real-world pragmatism: it works in Chrome 66 (released in 2018) and avoids features requiring newer runtime capabilities. The goal wasn’t performance at all costs, but rather maintaining strict backwards compatibility while delivering verifiable, client-side computation without leaking user data to servers.

Anubis challenges are designed to run entirely in the browser — verifying proof-of-work, resource usage, or behavioral signals before granting access to protected content. By moving logic into WebAssembly, Anubis gains deterministic execution, memory isolation, and faster startup than equivalent JavaScript — all without sacrificing its core privacy promise. Crucially, the WASM module is loaded and executed only when needed, and never communicates with external endpoints during evaluation.

The implementation leans heavily on Rust’s wasm32v1-none target, which produces baseline WebAssembly without optional features like threads or SIMD. This choice enforces #[no_std], eliminates dynamic memory allocation, and keeps binary size under 40 KB — small enough for low-bandwidth users and legacy devices. Developers also added graceful fallbacks: if WASM is disabled (e.g., via browser policy or user preference), Anubis falls back to a minimal, standards-compliant JavaScript path — and displays a clear message explaining why WASM is required.

What stands out isn’t just technical execution, but philosophy: Anubis treats browser diversity not as an obstacle to be abstracted away, but as a design constraint to be honored. Its maintainers explicitly rejected ‘progressive enhancement’ in favor of ‘conservative compatibility’ — supporting older browsers not for nostalgia, but because those users often face the greatest surveillance pressure and least control over their tooling. As one commenter noted, this reflects deeper values about who open-source software serves — and who gets left behind when compatibility is deprioritized.
