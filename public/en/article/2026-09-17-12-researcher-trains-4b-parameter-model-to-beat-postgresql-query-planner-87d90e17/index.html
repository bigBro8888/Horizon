Researcher trains 4B-parameter model to beat PostgreSQL query planner

News time: 2026-09-17T06:07:11.316816+00:00 · Source: hackernews

A researcher has demonstrated that a 4-billion-parameter machine learning model can generate query execution plans that run 81% faster than PostgreSQL’s native query planner—but only under tightly controlled, memory-resident, read-only conditions. The work, detailed on rohanbansal.com/qorl, uses a synthetic benchmark built from an 8 GB dataset (e.g., IMDb-like schema) fully loaded into RAM. Crucially, PostgreSQL’s shared_buffers were artificially limited—forcing the planner to rely more heavily on disk I/O assumptions—and all queries were warmed and measured after repeated runs to eliminate cold-cache noise.

This isn’t traditional rule-based or cost-model optimization. Instead, the model appears to learn patterns from thousands of query-plan pairs, likely using reinforcement learning or supervised imitation of high-performing plans. It doesn’t rewrite SQL or change indexes; it selects among available physical operators (e.g., nested loop vs. hash join, sequential scan vs. index scan) in ways that outperform PostgreSQL’s cost estimator on this specific workload. The speedup is real on the benchmark, but it reflects plan latency—not end-to-end query latency—and excludes planning time itself.

Critics quickly pointed out key limitations. As one Hacker News commenter noted, the setup lacks realistic OLTP characteristics: no concurrent writes, no index statistics beyond primary keys, no column correlations modeled in the optimizer, and no dynamic parameter changes mid-workload. Another raised concerns about hallucination—what happens when the model skips an index due to subtle input variation? And since LLMs (or large policy networks) don’t expose reasoning traces, debugging a misoptimized plan becomes guesswork, unlike PostgreSQL’s transparent EXPLAIN ANALYZE output.

Still, the experiment signals a meaningful shift: ML is moving beyond post-hoc indexing or caching hints into the core of query planning. While not production-ready, it challenges long-held assumptions about what makes a ‘good’ plan—and whether human-crafted heuristics still dominate in all regimes. For database engineers, the takeaway isn’t adoption, but awareness: the boundary between systems software and statistical modeling is blurring, and future optimizers may need both mathematical rigor and empirical generalization.
