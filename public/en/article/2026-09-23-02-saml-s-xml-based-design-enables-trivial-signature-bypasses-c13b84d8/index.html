SAML’s XML-based design enables trivial signature bypasses

News time: 2026-09-23T05:56:01.492089+00:00 · Source: hackernews

A scathing new analysis from Trail of Bits labels SAML not just flawed—but a 'fractal of bad design': every layer, from its XML foundation to cryptographic bindings and protocol flows, compounds insecurity. The core issue lies in how SAML ties authentication to XML Signature (XMLSig), a specification notoriously fragile in practice. As documented in academic and industry research, real-world SAML implementations routinely fail to validate signatures correctly—allowing attackers to strip, duplicate, or reposition signed elements without detection. One infamous example cited by developers is the default behavior of certain C-based XMLSig libraries: they would verify signatures not only against the intended public key but also against an HMAC key supplied by the attacker inside the SAML document—and even accept TLS certificates from arbitrary domains as valid signing keys.

This isn’t theoretical. Researchers have demonstrated XML Signature Wrapping (XSW) attacks that let adversaries forge authenticated sessions with minimal effort. A 2014 study confirmed these vulnerabilities are widespread across SAML validation frameworks, and recent AI-assisted audits (e.g., using Claude) have rediscovered similar flaws—highlighting how deeply embedded the problems are in parser logic and custom XML handling code. Unlike modern protocols built around stateless tokens and clear cryptographic boundaries, SAML treats identity assertions as mutable documents, inviting complexity where simplicity is needed.

The critique doesn’t stop at cryptography. Commenters on Hacker News point out that SAML reflects a broader era of over-engineering: when XML was seen as the universal solution for everything—including authentication, which is fundamentally about proving who you are, not marking up structured data. OIDC, while not perfect, shifts toward JSON Web Tokens (JWTs) with explicit algorithm declarations, audience checks, and standardized validation routines—though it too suffers from pitfalls like 'none' algorithm abuse and inconsistent library support.

Still, enterprise inertia keeps SAML alive. As one practitioner notes, SAML offers IdP-initiated flows and stable, if mediocre, interoperability across legacy systems—features OIDC hasn’t fully matched in broad deployment. Yet the growing consensus is clear: maintaining SAML means carrying technical debt that grows more dangerous with every integration. For security teams, the takeaway is urgent: treat SAML as a known-risk legacy component—not a neutral transport—and prioritize migration paths that reduce XML surface area and enforce strict signature verification.
