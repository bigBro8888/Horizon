Avoid hardcoding GitHub URLs in Go module paths

News time: 2026-09-28T06:48:34.840279+00:00 · Source: hackernews

A widely discussed blog post by Iain Campbell argues that Go developers should stop embedding GitHub.com URLs directly into their module paths — for example, using github.com/org/repo as the module path in go.mod. While this pattern is common and convenient, it creates an implicit dependency on GitHub’s infrastructure and domain. If a team migrates to GitLab, Bitbucket, or an internal Git server, every import statement, CI pipeline, and documentation link breaks unless manually updated — or unless workarounds like replace directives are applied across all dependent modules.

The article proposes using stable, organization-controlled domains instead — such as example.com/go/repo — to decouple the logical identity of a module from its physical hosting location. This approach aligns with Go’s design principle that the module path serves as a namespace, not a URL. As the Go Modules Reference states, the module path is the module’s unique identifier (combined with version), and becomes the import prefix for all its packages. A custom domain makes that namespace portable and future-proof.

However, the advice isn’t without tradeoffs. Several commenters raise practical concerns: domain ownership introduces new risks — expiration, registrar policy changes, or business dissolution could orphan packages just as surely as platform lock-in. One commenter cites VeriSign’s history of mass domain deletions; another warns that open-source maintainers are less likely to renew domains than Microsoft is to keep github.com online. Others point out that Go’s built-in replace directive already solves migration pain points locally — suggesting that domain abstraction may be over-engineering for many teams.

Still, the core argument resonates beyond Go: coupling code to transient infrastructure undermines long-term maintainability. Whether it’s GitHub URLs, cloud provider SDKs, or hardcoded S3 endpoints, architectural decisions made for convenience today often become technical debt tomorrow. The post doesn’t demand universal adoption — rather, it invites teams to consciously choose where they accept coupling, and to treat module paths as deliberate, durable identifiers — not accidental URLs.
