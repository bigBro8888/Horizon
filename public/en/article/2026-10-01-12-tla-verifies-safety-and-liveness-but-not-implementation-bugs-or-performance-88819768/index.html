TLA+ verifies safety and liveness—but not implementation bugs or performance

News time: 2026-10-01T07:09:55.647308+00:00 · Source: hackernews

TLA+ is a formal specification language designed to model and verify the behavior of concurrent and distributed systems—not their code. A recent article by Hillel Wayne clarifies exactly what TLA+ can and cannot check, offering practitioners a realistic map of its capabilities. At its core, TLA+ excels at verifying two foundational classes of properties: safety (nothing bad ever happens—e.g., no double-spending in a consensus protocol) and liveness (something good eventually happens—e.g., a request will eventually be processed). These are checked by exhaustively exploring reachable system states using the TLC model checker.

But TLA+ does not—and was never intended to—verify implementation correctness. It says nothing about whether your Rust or Java code matches the spec, nor whether it contains off-by-one errors, memory leaks, or incorrect use of libraries. Likewise, TLA+ abstracts away timing, hardware details, floating-point arithmetic, and real-world resource constraints. You cannot express or verify performance bounds (e.g., “latency stays under 100ms”) or hyperproperties (e.g., “no two users ever see inconsistent views”) directly in standard TLA+.

Another important boundary concerns memory models. As one commenter notes, TLA+ assumes sequential consistency by default; modeling weak memory semantics—like those found in modern CPUs or relaxed concurrency libraries—requires manually encoding memory reorderings, which quickly becomes unwieldy and error-prone. Similarly, while TLA+ specs are precise and executable via PlusCal or TLC, they are not programs: translating them into production code remains a human-driven, error-prone step.

The article resonates strongly with practitioners because it counters over-optimism about formal methods. Many engineers new to TLA+ assume it’s a silver bullet for bug-free systems. In reality, it’s a powerful but narrowly scoped tool—best used alongside testing, code reviews, and domain-specific verification tools like SPARK or Quint. As the Hacker News discussion shows, experienced teams often combine TLA+ for high-level design validation with other techniques for lower-level assurance.
