Turbopuffer v3 ditches vector database label for storage-first indexing

News time: 2026-10-02T06:58:44.044123+00:00 · Source: hackernews

In a bold architectural pivot, Turbopuffer has released version 3 — not as an upgrade to its prior vector database, but as a deliberate departure from the 'vector database' paradigm altogether. The new design treats approximate nearest neighbor (ANN) search not as the core engine, but as a secondary index layered atop durable, columnar object storage — much like how PostgreSQL or MySQL build B-tree or full-text indexes over tables. This shift reframes vector search as a capability of a broader data system, rather than a siloed service built exclusively for high-dimensional vectors.

The motivation stems from real-world scaling pain: earlier ANN-first systems suffer from write amplification, costly reindexing, and tight coupling between vector layout and storage. As one commenter notes, tuning indexing throughput had hit diminishing returns — because the bottleneck wasn’t the algorithm, but the underlying data model. Turbopuffer v3 instead anchors durability in immutable columnar fragments stored on object storage (e.g., S3), letting ANN indexes be rebuilt, swapped, or even omitted without compromising data integrity.

This approach aligns closely with emerging patterns in embedded and cloud-native systems. LanceDB, for example, also stores rows in columnar fragments and treats vector indexes as optional, detachable layers — a design praised by users building local code-graph tools who found traditional vector databases too slow or heavyweight. Turbopuffer’s implementation supports both vector and full-text (BM25) search from the same storage layer, enabling hybrid retrieval without data duplication or synchronization overhead.

Critically, this isn’t just theoretical. Turbopuffer v3 targets sub-200 ms p99 latency over 100 billion vectors per namespace — evidence that storage-first design doesn’t sacrifice performance. It also ships with a Python SDK and HTTP API, making it production-ready for developers already using SQLite-based or LanceDB-like stacks. The community response — 82 detailed comments and a 307 score — reflects broad resonance with the critique: the term 'vector database' may have outlived its technical usefulness.
