Git 3.0 will default to SHA-256 hashing in 2024

News time: 2026-10-02T06:58:44.044078+00:00 · Source: hackernews

Git is preparing for a foundational cryptographic upgrade: starting with version 3.0, new repositories will use SHA-256 instead of SHA-1 as the default object identifier hash. This change isn’t merely cosmetic—it reshapes how Git stores, verifies, and exchanges data across the entire ecosystem. The migration has been in development for years, with SHA-256 support stabilized in Git v2.42 (July 2023) and officially declared non-experimental. While backward compatibility remains a priority—existing SHA-1 objects can coexist and be referenced alongside SHA-256 ones—the shift introduces real engineering complexity, especially around submodules, hosting platforms, and tooling interoperability.

The debate intensified after a widely shared blog post titled Git 3.0’s Upcoming SHA-256 Default Will Be a Costly Mistake, which argued the move is technically unnecessary, economically wasteful, and logistically unfeasible at scale. It claimed SHA-1 remains practically secure for Git’s use case and that collision attacks like SHAttered don’t threaten repository integrity. But this view was quickly challenged by experts on Hacker News, who pointed out that SHAttered was not just theoretical: it demonstrated a real, efficient collision attack against SHA-1, and Git narrowly avoided impact only because attackers hadn’t yet optimized for Git’s specific object prefix format.

Critics also corrected factual errors in the original piece—such as misrepresenting GitHub’s current capabilities (it doesn’t yet support SHA-256 repos, but that’s a forge implementation gap, not a protocol limitation) and underestimating how quickly other tools adapted. Fossil SCM, for example, added SHA3-256 support just six days after SHAttered’s public release. Meanwhile, Git’s official transition plan explicitly addresses interoperability concerns: objects are bidirectionally mappable between SHA-1 and SHA-256, and references (like branch names or commit hashes in documentation) remain valid regardless of hash format.

Ultimately, the SHA-256 transition reflects a broader industry shift away from deprecated cryptographic primitives—not just for theoretical future-proofing, but because maintaining SHA-1 in core infrastructure increasingly conflicts with security policies, compliance requirements, and modern toolchain expectations. While the rollout demands coordination, it avoids the far costlier scenario of reacting to a real-world break after widespread adoption of vulnerable hashing.
