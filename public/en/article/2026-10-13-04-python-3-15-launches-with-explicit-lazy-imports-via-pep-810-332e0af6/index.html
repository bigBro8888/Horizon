Python 3.15 launches with explicit lazy imports via PEP 810

News time: 2026-10-13T07:40:20.491351+00:00 · Source: rss

Python 3.15 has officially arrived, marking a major milestone in the language’s evolution — and for the first time, developers can opt into lazy module loading with clear, explicit syntax. The release, announced by respected Python developer Simon Willison and curated by release manager Hugo van Kemenade, drops support for Python 3.10 while fully embracing features introduced in 3.11 and beyond. For maintainers of cross-version tools like Willison’s LLM CLI, this shift means dropping legacy compatibility burdens and adopting performance-focused innovations right away.

The standout feature is PEP 810: explicit lazy imports. Unlike earlier proposals such as PEP 690 — which attempted global, implicit lazy loading and was rejected by the Python Steering Council in 2022 — PEP 810 takes an opt-in, granular approach. Developers now write lazy import json or lazy from pathlib import Path, and the module is only loaded and executed the first time its symbols are accessed. This avoids costly eager initialization of heavy dependencies like sentence_transformers at startup — a real pain point for CLI tools, test runners, and plugin-based applications.

Another notable addition is unpacking in comprehensions (PEP 798), which brings concise, readable flattening to list, set, and dict comprehensions. For example, [ *L for L in lists ] cleanly replaces nested comprehensions like [x for L in lists for x in L]. While syntactically elegant, this change builds directly on Python 3.5’s PEP 448 unpacking generalizations — extending rather than overhauling existing patterns. It’s a small but welcome ergonomic win for data-heavy code.

What makes Python 3.15 especially significant is how it balances innovation with pragmatism. Rather than forcing lazy behavior system-wide — risking subtle bugs and debugging complexity — it gives developers precise control where it matters most: startup latency and memory footprint. And because laziness is local to each lazy import statement, it doesn’t cascade to transitive dependencies unless explicitly declared. That predictability is key for adoption in production tooling and frameworks.
