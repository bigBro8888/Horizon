Firefox users can now manually resume large downloads from one-time links

News time: 2026-10-13T07:40:21.012522+00:00 · Source: hackernews

Firefox has long lacked native support for resuming interrupted downloads when the source URL is a one-time link — a common scenario for secure file sharing. Unlike standard URLs that remain valid, one-time links expire after the first request, making traditional resume logic impossible: Firefox’s built-in downloader expects the same URL to accept Range requests, but the server rejects subsequent requests with errors like 404 or 410. A developer named Lunar Watcher recently documented a reliable manual workaround that lets users recover progress without restarting multi-gigabyte downloads from scratch.

The method hinges on Firefox’s internal download staging behavior. When a download begins, Firefox creates a .part file and writes incoming bytes to it. If the connection drops mid-transfer, that .part file retains all successfully received data — but Firefox won’t reuse it automatically upon retry because the new request starts fresh with a new .part file and no knowledge of prior offsets. The workaround involves pausing a new download attempt, swapping in the old .part file, and unpausing — effectively tricking Firefox into continuing from the correct byte position.

This isn’t a browser patch or configuration toggle; it’s a systems-level hack grounded in how HTTP range requests interact with stateless server-side link expiration. It requires no third-party tools, works with stock Firefox, and only needs basic file operations — though it demands careful timing and awareness of Firefox’s temporary file naming (e.g., avoiding accidental overwrites). The technique is especially valuable for users downloading large datasets, ISO images, or video archives from privacy-focused services that enforce one-time links for security.

The broader context reveals a tension between web security and usability. One-time links protect against unauthorized redistribution but break fundamental web expectations around resumability — a feature baked into HTTP/1.1 via the Range header and 206 Partial Content responses. Servers supporting byte serving could allow resumes even with short-lived tokens — if they embed offset-aware logic — but most don’t. Until Firefox implements smarter local state tracking or servers adopt more resilient token designs, workarounds like this fill a real gap. For now, it’s a pragmatic win for power users who prioritize control over convenience.
