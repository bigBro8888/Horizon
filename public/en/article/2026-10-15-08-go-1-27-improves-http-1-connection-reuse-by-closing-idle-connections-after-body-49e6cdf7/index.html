Go 1.27 improves HTTP/1 connection reuse by closing idle connections after body reads

News time: 2026-10-15T05:52:01.997587+00:00 · Source: hackernews

Go 1.27 introduces a subtle but impactful change to the net/http client’s handling of HTTP/1.1 connections: it now automatically closes idle connections after the response body has been fully read — rather than keeping them open indefinitely or relying solely on timeouts. This behavior prevents resource leaks in long-running clients that issue many requests but fail to consume response bodies completely, a surprisingly common mistake in real-world code. Previously, if a program called resp.Body.Close() without first reading all bytes (e.g., using io.Copy(ioutil.Discard, resp.Body)), the underlying TCP connection could remain idle and unreused, eventually exhausting the transport’s idle connection pool.

The change aligns Go’s behavior more closely with HTTP/1.1 semantics, where persistent connections are expected to be reused only when safe. By tying connection lifecycle to body consumption — not just header receipt — Go avoids holding onto connections that may no longer be usable due to incomplete reads or application logic errors. This is especially valuable for microservices, CLI tools, and scrapers that make bursty or irregular HTTP calls and often neglect proper body draining.

Importantly, this isn’t a new timeout mechanism. It’s a deterministic state transition: once the body reader returns io.EOF, the transport marks the connection as eligible for immediate closure — unless actively reused for another request before cleanup. The implementation avoids race conditions by coordinating with the body reader’s internal state, and it works transparently with standard patterns like json.NewDecoder(resp.Body).Decode(&v). However, as community comments note, edge cases remain — for example, json.Decoder may stop early on whitespace, leaving unread bytes and blocking reuse.

This improvement reflects Go’s pragmatic evolution: rather than over-engineering abstractions, the team observed widespread misuse in production (like the infamous drainAndCloseBody variants), then embedded the fix directly into the standard library. It doesn’t require code changes for most users — but developers who manually manage connections or rely on precise timing of Close() behavior should review their assumptions. For the broader ecosystem, it means fewer mysterious 'connection refused' or 'too many open files' errors in high-throughput HTTP clients.
