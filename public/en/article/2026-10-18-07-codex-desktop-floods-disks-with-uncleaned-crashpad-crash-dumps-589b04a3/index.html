Codex Desktop floods disks with uncleaned Crashpad crash dumps

News time: 2026-10-18T05:50:46.692738+00:00 · Source: hackernews

Developers using OpenAI’s Codex Desktop app are reporting a serious and persistent disk space issue: the application continuously generates large volumes of Crashpad pending dump files—.dmp binaries paired with JSON sidecar files—even when no crashes occur. These files accumulate silently in local storage, often growing to tens or even hundreds of gigabytes over days or weeks of normal use. Users describe waking up to full disks, sluggish system performance, and unexpected failures in builds or IDE integrations—all traced back to unmanaged artifact sprawl from Codex’s background processes.

The problem is not limited to edge cases. Multiple developers confirmed it across macOS and Windows, including those running Codex inside Docker containers and on Windows VMs connected via custom agents. One user reported 90 GB consumed by validation test artifacts alone during a financial automation project; another found thousands of screenshots and build artifacts littering git worktrees—none automatically cleaned up. The root cause appears tied to how Codex leverages Crashpad, Google’s open-source crash-reporting library, not just for crash diagnostics but also for on-demand process state capture during agent-driven workflows.

Crashpad itself is designed to be lightweight and reliable—but Codex’s usage pattern breaks that assumption. Instead of generating dumps only after crashes, Codex triggers them continuously during routine operations like code generation, test execution, and UI interaction. Each dump includes metadata-rich sidecar files, and because Codex doesn’t implement cleanup logic, these pending dumps remain indefinitely. This behavior contradicts Crashpad’s intended design, which expects clients to explicitly upload or discard dumps after capture.

Mitigation strategies have emerged organically from the developer community—not from official documentation. Top recommendations include enabling filesystem-level compression (e.g., ZFS on Linux/macOS), archiving old sessions with tools like sessionwiki, isolating Codex in Docker containers to contain disk impact, and switching to disk-usage visualizers like DaisyDisk for rapid triage. Still, none address the underlying issue: Codex lacks built-in artifact lifecycle management. As AI coding agents become central to engineering workflows, unbounded local storage growth threatens reliability, reproducibility, and trust in production tooling.
