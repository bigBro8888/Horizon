Railway forces API key rotation after credential leak causes outages

News time: 2026-10-22T06:05:39.885623+00:00 · Source: hackernews

On Wednesday, October 21st, Railway — a popular cloud platform for developers to deploy and manage applications — issued an urgent security disclosure confirming that unauthorized actors had accessed and exfiltrated API keys belonging to some of its users. The company immediately mandated all affected customers rotate their credentials. While this is a standard incident-response step, Railway’s execution created a cascading operational crisis: to prevent further misuse, it paused all builds system-wide. As a result, developers who rotated keys could not redeploy services to adopt the new credentials — leaving live applications broken, unresponsive, or misconfigured.

The timing amplified the pain. Multiple developers reported being woken up in the early hours of the morning across time zones to rotate keys — only to discover their services remained down because deployments were frozen. One European developer noted bitterly, “Which is worse: a stolen key or a broken product?” Others highlighted how the outage coincided with two other high-profile security events that same week: a critical PHP remote code execution vulnerability (PHP2Shell) and the eMudhra certificate compromise — suggesting a broader wave of infrastructure-level threats.

The incident also exposed real-world friction in DevOps security hygiene. Rotating secrets is widely recommended — best practices suggest doing so every 90 days — but Railway’s implementation lacked graceful transition support. Unlike robust CI/CD systems that allow dual-key coexistence (running old and new keys in parallel during rotation), Railway offered no such buffer. Developers using third-party integrations like OpenRouter saw unexpected charges as leaked keys were abused before rotation — one user reported $2 spent on Anthropic’s Opus 5.5 and Fable models. Meanwhile, automated tools like Muse buried the urgency of the alert among routine notifications, delaying response.

Beyond technical failure, the episode raised questions about transparency and coordination. A Postiz founder claimed his service was already compromised and actively exploited before Railway publicly acknowledged the issue — only speaking up after he called attention to it on X. For many teams, the outage hit during critical windows: one engineer described it as the first vacation day they’d taken all year — now consumed by firefighting. Ultimately, this wasn’t just a bug fix; it was a stress test of trust in modern developer infrastructure — where security actions, if poorly orchestrated, can inflict more damage than the threat itself.
